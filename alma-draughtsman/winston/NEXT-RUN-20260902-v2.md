## 1. The rainbow collapse — diagnosed, with evidence

Three paintings today came out as saturated rainbow noise: pair02, pair08, and the 4K
Alma run (outALMA4K). Eight others were fine.

**Measured on the paintings (PC, family-out/*_pair.png, painted half vs source half):**

| painting | source chroma | painted chroma | ratio | pixels pinned to pure colour |
|---|---|---|---|---|
| pair02 (collapsed) | 0.110 | 0.371 | 3.4x | 8.3 % |
| pair08 (collapsed) | 0.077 | 0.390 | 5.1x | 4.9 % |
| alma4k (collapsed) | 0.130 | 0.386 | 3.0x | 7.7 % |
| the 8 good ones | 0.06-0.36 | within ±0.01 of source | 1.0-1.1x | 0.0 % |

**Measured on the checkpoint (eran4, outALMA4K/painter.pt vs healthy nets):**

| | collapsed | forever (healthy) | almaV2 (healthy) |
|---|---|---|---|
| mean \|colour logit\| | **23,894** | 2.0 | 1.1 |
| mean \|width logit\| | **45,451** | 5.7 | 2.2 |
| mean \|xy logit\| | **10,874** | 0.6 | 0.5 |
| colour logits beyond ±8 | **100 %** | 1 % | 0 % |
| NaN anywhere | no | no | no |
| max \|weight\| | 3.9 | 3.8 | 0.9 |
| decide.4 weight norm | 130 | 185 | 63 |

The loss log of the collapsed run (runALMA.log) is frozen to five decimals for
5,000 steps: `0.24602` x5. A frozen loss under AdamW means the gradient is *exactly*
zero.

**Reading:** it is not the weights that blow up (norms are the same or smaller than
healthy). The layers align so that the activations run off to ~10^4; every sigmoid
(colour, width) and tanh (position) pins; a pinned sigmoid has zero gradient; Adam
steps by the learning rate regardless of gradient size, so once the logits are past
the cliff nothing ever pulls them back. Pinned RGB sigmoids = pure red/green/blue/
black/white strokes = "rainbow noise".

**What the three collapsed runs share that the eight good ones do not:** nothing in the
flags — pair02 and pair08 ran with the identical command, seed (1933 is hard-coded)
and settings as pair01/03/04/05/06/07/09, and the 4K Alma run collapsed within the
first 1,200 steps of a `--resume` from forever/painter.pt while the OneCycle warm-up
took the lr to its peak (1e-3) on an already-trained net. The instability is
structural (unbounded logits + saturating nonlinearities + Adam), and which image
trips it is data-dependent. runBIG.log shows the same event in mid-run (mse 0.032 →
0.12975 at step 10000, then frozen).

## 2. What v2 changes, and why

All three code changes are **flags that default OFF**: with no flags the new
winston.py is bit-identical to the old one (measured: max|diff| = 0.000e+00 on the
same weights and image), so the v1 loop's next cycle is unaffected.

| change | why | proof |
|---|---|---|
| `--logit-cap 12` | a hinge on \|logit\| above 12 — the one gradient that survives a pinned sigmoid, pointing home. sigmoid(12)=0.99999, nothing is lost. | healthy widths sit at 5-7, well under the cap |
| `--guard --guard-every 100` | every 100 steps: pinned-logit fraction > 50 %, painted chroma > 2x source, worse than BLANK (once it has beaten BLANK), or NaN → roll back to the last good snapshot (net + Adam state), halve the lr. A collapsed final state is never saved. | forced collapse (resume at lr 0.5): 8 detections, 8 rollbacks, the saved painter.pt is the good snapshot (PAINTER 0.00582 = the pre-collapse number) |
| `--recompute` | gradient checkpointing per stroke chunk — the OOM scar was the retained autograd graph. | gradient max\|diff\| = 0.000e+00; peak memory 7.08 → 1.81 GB at 192px, 12.23 → 2.87 GB at 256px (b8, 120 strokes, chunk 16) |
| `--size 256` (was 192) | the loss sees 1.78x the pixels; a painter cannot paint detail it never sees. This is the "sharper" lever. Affordable only because of --recompute. | full v2 config timing: measured 29.2 s/step and **peak 8.4 GB** for b16 / 256px / 800 strokes / chunk 16 / recompute — measured WHILE the v1 cycle held the GPU at 96 %, so it is an upper bound; v1 alone runs 2.9 s/step at 192px, so the expected solo cost is ~7 s/step (1.78x pixels, ~1.3x recompute). Read the real number off the first v2 step prints. |
| `--lr 5e-4` (was 1e-3) | every cycle re-warms OneCycle to its peak on an already-trained net; the 4K Alma run collapsed inside that warm-up. | runALMA.log |
| `trainset-iddo-alma-v2` = 93 photos (was 19) | Iddo: "maybe enlarge the corpus". The 19 + 4 Alma-memorial photos from the PC + 70 curated family photos (people only, one per burst, no screenshots/food/flyers) from the iCloud-stream backup already on eran4. **EXIF orientation baked in** — 8 of the old 19 carry orientation 3/6/8 and the loader ignores EXIF, so the painter has been learning them sideways/upside-down. | MANIFEST.tsv lists file, origin, source path, size, EXIF tag |
| `--steps 2000` per cycle | a 256px step costs more (7-15 s); 2000 keeps one painting per night even at the slow end. Override: `WINSTON_STEPS` env in the unit. | |
| `forever-v2/` | its own checkpoint chain, seeded once from forever/painter.pt (strokes 800 = 800, so --resume is legal). forever/ is never written. | |

Not changed: `--strokes 800`, `--chunk 16`, `--colour-w 2.5`, `--detail-w 3`.

## 3. How to read the first v2 output

Every run now prints one extra line in the verdict:

    CHROMA source 0.xxx | painted 0.xxx (x1.0x) | colour logits pinned x.x%

Healthy = ratio 1.0-1.15 and pinned ~1 %. Collapse = ratio ~3 and pinned 100 %.
`GUARD: n rollback(s)` says whether the fence was ever needed. Compare
`forever-v2/paint-00..07.png` (fam00..fam07, same first eight as forever/) with
`forever/paint-00..07.png`; the v1 numbers to beat are cycle 1's
`BLANK 0.04997 | PAINTER 0.01452 | BUSY 0.02714` (on 19 images at 192px — the v2 mse
is measured on 93 images at 256px, so it is a harder number; the pictures decide).
